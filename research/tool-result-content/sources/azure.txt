	 <div class="content"><p>Use the Azure OpenAI Responses API to generate stateful, multi-turn responses. It brings together capabilities from chat completions and the Assistants API in one unified experience. Use <a href="responses-multi-agent" data-linktype="relative-path">multi-agent orchestration</a> to delegate independent work to parallel subagents, or use <a href="tool-search" data-linktype="relative-path">tool search</a> to load tool definitions only when the model needs them. The Responses API also supports the <code>computer-use-preview</code> model that powers <a href="../../../foundry-classic/openai/how-to/computer-use" data-linktype="relative-path">Computer use</a>.</p>
<p>For complete request and response parameter descriptions, see the <a href="/en-us/rest/api/microsoft-foundry/azureopenai/responses?view=rest-microsoft-foundry-v1-preview&amp;preserve-view=true" data-linktype="absolute-path">Responses API parameter reference</a>.</p>
<h2 id="prerequisites">Prerequisites</h2>
<ul>
<li>A deployed Azure OpenAI model.</li>
<li>An authentication method:
<ul>
<li>API key (for example, <code>AZURE_OPENAI_API_KEY</code>), or</li>
<li>Microsoft Entra ID (recommended).</li>
</ul>
</li>
<li>Install the client library for your language:
<ul>
<li><strong>Python</strong>: <code>pip install openai azure-identity</code></li>
<li><strong>.NET</strong>: <code>dotnet add package OpenAI</code> and <code>dotnet add package Azure.Identity</code></li>
<li><strong>JavaScript/TypeScript</strong>: <code>npm install openai @azure/identity</code></li>
<li><strong>Java</strong>: Add <code>com.openai:openai-java</code> and <code>com.azure:azure-identity</code> to your project.</li>
</ul>
</li>
<li>For REST examples, set <code>AZURE_OPENAI_API_KEY</code> (API key flow) or <code>AZURE_OPENAI_AUTH_TOKEN</code> (Microsoft Entra ID flow).</li>
</ul>

  input=[
    *compacted_response.output,
    {"role": "user", "content": "What is the capital?"}
  ]
)

</code></pre>
<h3 id="server-side-compaction">Server-side compaction</h3>
<p>You can also use server-side compaction directly in Responses (<code>POST /responses</code> or <code>client.responses.create</code>) by setting <code>context_management</code> with a <code>compact_threshold</code>.</p>
<ul>
<li>When the output token count crosses the configured threshold, the Responses API automatically runs compaction.</li>
<li>In this mode, you do not need to call <code>/responses/compact</code> separately.</li>
<li>The response includes an encrypted compaction item.</li>
<li>Server-side compaction will work when you set store=false on your Responses create requests.</li>
</ul>
<p>The compaction item carries forward the essential prior state and reasoning into the next turn using fewer tokens. It is opaque and not intended to be human-readable.</p>
<p>If you are using stateless input-array chaining, append output items as usual. If you are using <code>previous_response_id</code>, pass only the new user message on each turn. In both patterns, the compaction item carries the context needed for the next window.</p>
<div class="TIP">
<p>Tip</p>
<p>After appending output items to the previous input items, you can drop items that came before the most recent compaction item to keep requests smaller and reduce long-tail latency. The latest compaction item carries the necessary context to continue the conversation. If you use <code>previous_response_id</code> chaining, do not manually prune.</p>
</div>
<h4 id="flow">Flow</h4>
<ol>
<li>Call <code>responses</code> as usual. Add <code>context_management</code> with <code>compact_threshold</code> to enable server-side compaction.</li>
<li>If the output crosses the threshold, the service triggers compaction, emits a compaction item in the output stream, and prunes the context before continuing inference.</li>
<li>Continue the conversation using one of these patterns:
<ol>
<li>Stateless input-array chaining: append output items, including compaction items, to the next input array.</li>
<li><code>previous_response_id</code> chaining: pass only the new user message on each turn and carry the latest response ID forward.</li>
</ol>
</li>
</ol>
<h4 id="example">Example</h4>
<pre><code class="lang-python">conversation = [
  {
    "type": "message",
    "role": "user",
    "content": "Let's begin a long coding task.",
  }
]

while keep_going:
  response = client.responses.create(
    model="MODEL_NAME",
    input=conversation,
    store=False,
    context_management=[{"type": "compaction", "compact_threshold": 200000}],
  )

  conversation.append(
    {
      "type": "message",
       "role": "user",
      "content": get_next_user_input(),

<h2 id="handle-guardrails-and-content-filtering">Handle guardrails and content filtering</h2>
<p>Guardrails (content filters) are applied at the deployment level and run automatically on every Responses API call, so they protect both the input you send and the output the model generates. You configure guardrails separately. For more information, see <a href="../../guardrails/how-to-create-guardrails" data-linktype="relative-path">Configure guardrails and controls</a>. This section shows how to detect and handle guardrail results when you call the Responses API.</p>
<p>The Responses API surfaces guardrail results differently from chat completions. Instead of the <code>prompt_filter_results</code> and <code>content_filter_results</code> fields that chat completions return, the response object includes a top-level <code>content_filters</code> array. Each entry describes one filter result.</p>
<table>
<thead>
<tr>
<th>Field</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>blocked</code></td>
<td>Whether the content was blocked.</td>
</tr>
<tr>
<td><code>source_type</code></td>
<td>Whether the result applies to the <code>prompt</code> (input) or the <code>completion</code> (output).</td>
</tr>
<tr>
<td><code>content_filter_results</code></td>
<td>The category results, such as <code>hate</code>, <code>sexual</code>, <code>violence</code>, and <code>self_harm</code> with severity levels, plus optional categories such as <code>jailbreak</code>, <code>indirect_attack</code>, <code>protected_material_text</code>, and <code>protected_material_code</code>.</td>
</tr>
<tr>
<td><code>content_filter_offsets</code></td>
<td>The character offsets that the result applies to.</td>
</tr>
</tbody>
</table>

<p>Note</p>
<p>The <code>content_filters</code> array is a Microsoft Foundry extension that isn't part of the base OpenAI response schema, so the SDKs don't expose a typed property for it. Read it as a raw or extra field, as shown in the following examples.</p>

<h2 id="code-interpreter">Code Interpreter</h2>
<p>The Code Interpreter tool enables models to write and execute Python code in a secure, sandboxed environment. It supports a range of advanced tasks, including:</p>
<ul>
<li>Processing files with varied data formats and structures</li>
<li>Generating files that include data and visualizations (for example, graphs)</li>
<li>Iteratively writing and running code to solve problems—models can debug and retry code until successful</li>
<li>Enhancing visual reasoning in supported models (for example, o3, o4-mini) by enabling image transformations such as cropping, zooming, and rotation</li>
<li>This tool is especially useful for scenarios involving data analysis, mathematical computation, and code generation.</li>
</ul>

<h3 id="containers">Containers</h3>
<div class="IMPORTANT">
<p>Important</p>
<p>Code Interpreter has <a href="https://azure.microsoft.com/pricing/details/cognitive-services/openai-service/" data-linktype="external">additional charges</a> beyond the token-based fees for Azure OpenAI usage. If your Responses API calls Code Interpreter simultaneously in two different threads, two Code Interpreter sessions are created. Each session incurs per-minute charges, with a minimum charge of five minutes. A session remains active as long as you access its container within the 20-minute idle timeout.</p>
</div>
<p>The Code Interpreter tool requires a container—a fully sandboxed virtual machine where the model can execute Python code. Containers can include uploaded files or files generated during execution.</p>
<p>To create a container, specify <code>"container": { "type": "auto", "file_ids": ["file-1", "file-2"] }</code> in the tool configuration when creating a new Response object. This automatically creates a new container or reuses an active one from a previous code_interpreter_call in the model's context. The <code>code_interpreter_call</code> in the output of the API will contain the <code>container_id</code> that was generated. This container expires if it is not used for 20 minutes.</p>
<p>The following file limits apply:</p>
<ul>
<li>A request can include up to 50 file IDs.</li>
<li>A container can hold up to 1,000 files in total, including input files and files generated by Code Interpreter.</li>
</ul>
<h3 id="file-inputs-and-outputs">File inputs and outputs</h3>
<p>When running Code Interpreter, the model can create its own files. For example, if you ask it to construct a plot, or create a CSV, it creates these images directly on your container. It will cite these files in the annotations of its next message.</p>
<p>Any files in the model input get automatically uploaded to the container. You do not have to explicitly upload it to the container.</p>

<h3 id="image-input-requirements">Image input requirements</h3>
<p>The following table lists the supported file types for image inputs.</p>
<table>
<thead>
<tr>
<th>File type</th>
<th>MIME type</th>
</tr>
</thead>
<tbody>
<tr>
<td>PNG</td>
<td><code>image/png</code></td>
</tr>
<tr>
<td>JPEG</td>
<td><code>image/jpeg</code></td>
</tr>
<tr>
<td>WebP</td>
<td><code>image/webp</code></td>
</tr>
<tr>
<td>Non-animated GIF</td>
<td><code>image/gif</code></td>
</tr>
</tbody>
</table>
<p>In a single request, you can include up to 50 images. Each individual image file must be under 50 MB, and the combined size of all images in the request must also be under 50 MB.</p>
<p>Images must meet these additional requirements:</p>
<ul>
<li>The image must be relevant to the prompt; the model isn't designed for unrelated visual content.</li>
<li>Images shouldn't contain harmful or sensitive content that violates content policies.</li>
<li>Image files can't be corrupted or unreadable. If the model can't process an image, the request fails.</li>
</ul>
<h3 id="choose-an-image-detail-level">Choose an image detail level</h3>
<p>Use the <code>detail</code> property on an <code>input_image</code> content part to control how the model processes the image. Lower detail uses fewer tokens and is faster, while higher detail uses more tokens but lets the model capture finer features.</p>
<pre><code class="lang-json">{
  "type": "input_image",
  "image_url": "&lt;image_url&gt;",
  "detail": "high"
}
</code></pre>
<p>The following table describes each detail level.</p>
<table>
<thead>
<tr>
<th>Detail level</th>
<th>Description</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>low</code></td>
<td>The model uses a lower-resolution version of the image. This option uses the fewest tokens and produces the fastest response, but the model might miss fine details.</td>
</tr>
<tr>
<td><code>high</code></td>
<td>The model uses a higher-resolution version of the image. This option captures finer details but uses more tokens and takes longer to respond.</td>
</tr>
<tr>
<td><code>auto</code></td>
<td>The default. The model selects the appropriate detail level based on the image and the prompt.</td>
</tr>
</tbody>
</table>
<h3 id="image-input-limitations">Image input limitations</h3>
<p>Vision-enabled models have the following limitations:</p>
<ul>
<li><strong>Medical images</strong>: The model isn't suitable for interpreting specialized medical images such as CT scans and shouldn't be used for medical advice.</li>
<li><strong>Non-English text</strong>: The model might not perform optimally when handling images that contain text in non-Latin alphabets, such as Japanese or Korean.</li>
<li><strong>Small text</strong>: Enlarge text within an image to improve readability, but avoid cropping out important details.</li>
<li><strong>Rotation</strong>: The model might misinterpret rotated or upside-down text and images.</li>
<li><strong>Visual elements</strong>: The model might struggle with graphs or text where colors or styles—such as solid, dashed, or dotted lines—vary.</li>
<li><strong>Spatial reasoning</strong>: The model has difficulty with tasks that require precise spatial localization, such as identifying chess positions.</li>
<li><strong>Accuracy</strong>: The model might generate incorrect descriptions or captions in some cases.</li>
<li><strong>Image shape</strong>: The model has difficulty with panoramic and fisheye images.</li>
<li><strong>Metadata and resizing</strong>: The model doesn't process original file names or metadata, and images are resized before analysis, which affects their original dimensions.</li>
<li><strong>Counting</strong>: The model might give approximate counts for objects in images.</li>
<li><strong>CAPTCHAs</strong>: For safety reasons, a system is in place to block the submission of CAPTCHAs.</li>
</ul>
<h2 id="file-input">File input</h2>
<p>Models with vision capabilities support PDF input. PDF files can be provided either as Base64-encoded data or as file IDs. To help models interpret PDF content, both the extracted text and an image of each page are included in the model's context. This is useful when key information is conveyed through diagrams or non-textual content.</p>
<div class="NOTE">
<p>Note</p>
<ul>
<li>All extracted text and images are put into the model's context. Make sure you understand the pricing and token usage implications of using PDFs as input.</li>
<li>In a single API request, you can include more than one file, but each file must be under 50 MB. The combined limit across all files in the request is 50 MB.</li>
<li>Only models that support both text and image inputs can accept PDF files as input.</li>
<li>A <code>purpose</code> of <code>user_data</code> is currently not supported. As a temporary workaround you will need to set purpose to <code>assistants</code>.</li>
</ul>
</div>

<h3 id="approvals">Approvals</h3>
<p>By default, the Responses API requires explicit approval before any data is shared with a remote MCP server. This approval step helps ensure transparency and gives you control over what information is sent externally.</p>
<p>We recommend reviewing all data being shared with remote MCP servers and optionally logging it for auditing purposes.</p>
<p>When an approval is required, the model returns a <code>mcp_approval_request</code> item in the response output. This object contains the details of the pending request and allows you to inspect or modify the data before proceeding.</p>
<pre><code class="lang-json">{
  "id": "mcpr_682bd9cd428c8198b170dc6b549d66fc016e86a03f4cc828",
  "type": "mcp_approval_request",
  "arguments": {},
  "name": "fetch_azure_rest_api_docs",
  "server_label": "github"
}
</code></pre>
<p>To proceed with the remote MCP call, you must respond to the approval request by creating a new response object that includes an mcp_approval_response item. This object confirms your intent to allow the model to send the specified data to the remote MCP server.</p>

<h2 id="background-tasks">Background tasks</h2>
<p>Background mode lets you run long-running tasks asynchronously with reasoning models such as <code>o3</code> and <code>o1-pro</code>. It's useful for complex tasks that can take several minutes to complete (for example, Codex- or Deep Research-style agents). When a request is sent with <code>"background": true</code>, the task is processed asynchronously, and you poll for its status.</p>
<h3 id="start-a-background-task">Start a background task</h3>
<p>Set <code>background=true</code> on the request to queue the task. The service returns immediately with a response ID and a <code>queued</code> status — use that ID to poll, stream, or cancel the task.</p>

<p>Background responses currently have a higher time-to-first-token latency than synchronous responses. Improvements are underway to reduce this gap.</p>
<h3 id="limitations">Limitations</h3>
<ul>
<li>Background mode requires <code>store=true</code>. Stateless requests are not supported.</li>
<li>You can only resume streaming if the original request included <code>stream=true</code>.</li>
<li>To cancel a synchronous response, terminate the connection directly.</li>
</ul>
<h3 id="resume-streaming-from-a-specific-point">Resume streaming from a specific point</h3>
<p>If a streaming connection drops, you can resume from a known event by passing <code>stream=true</code> along with <code>starting_after=&lt;sequence_number&gt;</code> on a <code>GET</code> to the response. The service replays events emitted after that sequence number.</p>
<pre><code class="lang-bash">curl -N -X GET "https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/responses/&lt;response_id&gt;?stream=true&amp;starting_after=42" \
  -H "Content-Type: application/json" \
  -H "api-key: $AZURE_OPENAI_API_KEY"
</code></pre>
<h2 id="encrypted-reasoning-items">Encrypted reasoning items</h2>
<p>When you use the Responses API in stateless mode (<code>store=false</code>), you must still preserve reasoning context across conversation turns. To do this, include encrypted reasoning items in your requests.</p>
<p>To retain reasoning items across turns, add <code>reasoning.encrypted_content</code> to the <code>include</code> parameter. The response then contains an encrypted version of the reasoning trace, which you can pass to future requests.</p>

<p>Compared to the standalone Image API, the Responses API offers two advantages:</p>
<ul>
<li><strong>Streaming</strong>: Display partial image outputs during generation to improve perceived latency.</li>
<li><strong>Flexible inputs</strong>: Accept image file IDs as inputs in addition to raw image bytes.</li>

<h3 id="why-was-my-api-session-ended-as-a-precaution">Why was my API session ended as a precaution?</h3>
<p>When using Astra models, to ensure agents interpret and follow your instructions correctly, we have a system that stops sessions in Responses API if it detects the agent may not have been interpreting your instructions correctly in cases such as transferring sensitive data, accessing sensitive data, or making destructive changes. If your session was ended, this does not necessarily mean the agent made a mistake, only that it is worth reviewing the agent's actions to ensure it interpreted and followed your instructions correctly.</p>
<h3 id="which-api-requests-are-monitored-by-this-system">Which API requests are monitored by this system?</h3>
<p>The same system described above asynchronously monitors requests to Astra in the Responses API. The Chat Completions API is not scanned by this specific monitoring system. We recommend using the Responses API for the greatest degree of performance and safety for agentic use cases.</p>
<h4 id="how-to-detect-that-a-conversation-has-been-ended-in-the-api-by-this-system">How to detect that a conversation has been ended in the API by this system?</h4>
<p>When the safety system detects that an agent might have interpreted instructions incorrectly in a significant way, the API returns a safety annotation code misalignment-enforcement. In this case, the given session is unable to be resumed.</p>
<h4 id="what-should-my-application-do-if-such-a-case-is-detected">What should my application do if such a case is detected?</h4>
<p>You may want to consider setting up some system to enable somebody to review the actions that the agent took in such conversations, for example by providing a UI to the end-user to review. Once a conversation is stopped for this reason in the API, it is unable to be resumed.</p>
