# 2026-09-29 — Opaque objects keep an order JavaScript would change: vectors that can see it

**Status: VECTORS + HARNESS (enforce the existing rule INV-002 / serde-rules
omission rule 3; the one spec edit is a clarifying sentence under INV-002,
ratified below). No recorded fixture, golden or mapping rule changes.**

## The gap

INV-002 and omission rule 3 say opaque payloads round-trip exactly, and
since 2026-09-25 the harness checks their key order
(changes/2026-09-25-opaque-key-order.md). But a JavaScript object does not
keep insertion order for every name: ECMA-262 (OrdinaryOwnPropertyKeys)
enumerates array-index names (`"0"`, `"10"`, `"2024"`: canonical digits
below 2^32 − 1) first, ascending, then the other names in insertion
order. `{"reasoning": …, "2024": …}` is enumerated `"2024"` first however
it was built, parsed or copied.

No vector before this one held such an object: every opaque object in the
corpus has either no array-index name or only one (`logit_bias:
{"1234": -100}`). So lm15-ts reordered, on both sides, and passed 1,788 of
1,788:

- **Built.** A `json_schema` response_format or a tool's parameters with
  `reasoning` before `2024` went out `2024` first. Under strict structured
  output a model writes properties in schema order (OpenAI documents it;
  Gemini's `propertyOrdering`; lm15-go's live smoke, 2026-09-26), so the
  answer was written before the reasoning meant to produce it. A tool
  call's input sent back in the history, `extensions` values and a
  DataPart's JSON text were reordered the same way.
- **Read.** A reply's tool call arguments `{"reasoning": …, "2024": …}`
  came back `2024` first, and went out that way on the next turn.

Found by a functai review (TypeScript stage 1, 2026-09-29): lmcc keeps
member order under a registered symbol, and lm15's strict JSON check
refused the symbol; the workaround, plain copies, sent JavaScript's order.

## What changed

- `mapping/opaque-order.json`, generated by
  `tools/make_opaque_order_vectors.py` (PROTOCOL.md, "The `mapping`
  direction"):
  - 7 `build` vectors, each built for openai, openai_chat, anthropic and
    gemini (25 cases): a tool's parameters, a nested schema with index
    names out of numeric order (`"10"` before `"9"`), a `json_schema`
    response_format, a tool call's input in the history, an `extensions`
    value, an object of index names only (Chat Completions `logit_bias`),
    and a DataPart.
  - 8 `parse` vectors: each dialect's complete and streamed tool call
    reply. Each body is a recorded reply (`derived_from`) with the tool
    call's arguments replaced, in every place the reply carries them, and
    re-split over the same number of fragments when it streams them.
    These bodies are hand-authored and claim nothing about a provider;
    `tools/test_mapping_vectors.py` re-derives each one from its source.
- `harness/check.py`: the mapping direction runs them. An object is found
  by its member names, not by equality, because the existing
  `opaque_order_difference` passes an object an adapter rewrites or drops
  without a word. Strings holding JSON are searched too (a Chat
  Completions `arguments`, a DataPart's text), which the byte-free
  comparison never looked inside.
- `serde/canonical.json`: 7 cases, one per opaque field (`parameters`, a
  builtin tool's `config`, a tool call's `input`, a DataPart's `value`,
  `response_format` and `extensions`, continuation `data`,
  `provider_data`).
- A harness fix found on the way: in the `serde` direction a `tool`
  value's own `config` (a builtin tool's) was not treated as opaque, so its
  order was never checked. It is now.
- `harness/selftest.py`: three mutations that enumerate objects the way a
  JavaScript object does (`index_names_first` for a build,
  `index_names_first_read` for a streamed read, `index_names_first_serde`),
  each caught.
- `spec/invariants.md` INV-002: one sentence saying that member order is
  part of byte-exact even where the host's own object type would change
  it.

The fix in lm15-ts: `parseJson` records a member order JavaScript would
change under the registered symbol `lm15.memberOrder` (not enumerable),
`stringifyJson` writes it, `isStrictJson` accepts a well-formed record, and
`orderedObject` / `setMember` / `memberNames` let a caller state and read an
order (its docs/port-notes.md, the stated deviation for JavaScript
literals). lmcc keeps member order under the same symbol, so what it builds
reaches the wire in its order.

## Not covered

- **A JavaScript literal.** `{reasoning: …, "2024": …}` written in
  TypeScript source is reordered by the language before any library sees
  it; no vector can reach that. lm15-ts documents it next to its `1.0`
  literal deviation and offers a way to state the order.
- **An object an adapter rewrites (INV-050's judgment schemas).** The
  judgment vectors are not repeated here: a judgment schema's properties
  are the judgments' own, and a property named like an index would be a
  judgment named like an index. Adapter unit tests cover the copy.
- **Live traffic.** No case was recorded: the property is lm15's own, not
  a provider's, and the behavioural consequence (a model writes in schema
  order) is already evidenced (changes/2026-09-25-opaque-key-order.md).
