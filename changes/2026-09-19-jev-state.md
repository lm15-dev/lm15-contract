# 2026-09-19 — Jev's state is the one user part, verbatim; and a data part on a text wire is its JSON

Ratification: Maxime Rivest, 2026-09-19, in session ("What I want is
that our request format by default, the easy way, the simple way, would
lead a user to make the most native and natural JEV request as they
kind of have it on their websites"; "yes, ok do it go"). Amends D6 of
`changes/2026-09-17-judgments.md`. The judgments surface is provisional
(SCOPE.md) and unreleased; the break below is taken now rather than
carried.

## The problem

D6 (2026-09-17) built Jev's `state` from lm15's chat shape: a single
user text part became a string, a single user data part its value, and
anything else — a system prompt, several messages — became
`{"system": <text>, "messages": [{"role", "content"}]}`.

Jev has no system prompt and no conversation shape. Its docs
(`docs.typesafe.ai/concepts/state`, `primitives`, `api`, read
2026-09-19) define `state` as `string | object | array` — "the material
you would present to a panel of experts" — and put everything else in
the two native places: supporting context as a **named key of the
state** (`{"ticket_message": …, "refund_policy": …}`), and framing in
each question's **`instructions`**, which point at state keys with
backtick paths (`` `ticket.messages[0].text` ``). Question IDs are not
shown to the model. Neither `system` nor `{role, content}` appears
anywhere in Jev's documentation.

Three faults followed from D6's wrapper, all measured live on
2026-09-19 (jev-latest; same note, same three questions):

1. **It costs tokens.** The wrapper around a string added 49 input
   tokens (455 → 504); around a `{note, price_eur}` object, 51 (470 →
   521). The system text itself is 27 of those; the rest is the shape.
2. **It buries the caller's object.** With a system prompt set, a user
   data part `{note, price_eur}` reached the wire as
   `state.messages[0].content[0].note` — three levels down, and inside
   a one-element array, because both ports rendered a data-part message
   through the text-message path. No one would write that path.
3. **It is invented.** The `{system, messages}` object is lm15's, not
   Jev's; a request built "the easy way" in lm15 did not produce the
   request in Jev's own quick start.

A second, related fault: `types.md §DataPart` says a data part in a
user message is "JSON text on wires that take only text". At the
2026-09-17 pin no chat dialect did that: the Responses dialect refused
it (MAP-10), and the Chat, Anthropic and Gemini dialects rendered it as
an **empty text** — the input was lost and the call still cost. Both
ports, measured 2026-09-18 (website `tests/judge_examples.test.ts`).

## Decisions

**D1 — The state is the one user part, verbatim (replaces D6).** A
typesafe request carries exactly one message, `role: user`, with
exactly one part, text or data. `state` is that part's `text` (a
string) or its `value` (any JSON: object, array, scalar), byte for
byte. Nothing is added, wrapped or renamed. The request a caller writes
the simple way is the request on `docs.typesafe.ai/api`.

**D2 — Everything Jev has no slot for is refused, with the native
place named.** `UnsupportedFeatureError` before any wire (MAP-13
condition b), `feature` as given:
- `system` present → `feature: "system"`. Message: Jev has no system
  prompt; put context in the state as a named key
  (`data({"policy": …, "note": …})`), or the framing in each question's
  `description`.
- more than one message → `feature: "messages"`. Message: Jev judges one
  state; put a transcript in the state as an array or object
  (`data({"messages": [...]})`), where a question can point at a turn.
- one message with more than one part → `feature: "messages[0].parts"`.
- a message that is not `user` → `feature: "messages[0].role"`.
- media, tool calls, tool results, tools, tool_choice: unchanged (D8).

Refusing rather than merging is the decision: any merge (a `system` key,
a folded question instruction) is a shape the adapter invents, costs
tokens the caller did not ask for, and hides where the text went. With
D1+D2 the adapter has no mapping logic left for the state.

**D3 — A data part on a text wire is its compact JSON.** In a
`user`/`system`/`developer` message, a data part reaches the Responses
wire as `input_text`, the Chat wire as `text`, Anthropic as a `text`
block and Gemini as a `text` part, whose text is the part's `value`
rendered by the port's canonical JSON serializer (no whitespace; an
opaque payload, so numbers as written — `docs/serde-rules.md` §Number
rule 4). Nothing is prefixed or explained: the value is what the caller
gave. An assistant data part (a judged answer replayed into a later
turn) renders the same way. This is the rule `types.md §DataPart`
already stated; it is now receipted and tested.

**D4 — The playground.** Judge mode's "Instructions" and
"Conversation" shapes, on typesafe, become what the caller would write:
the instructions a named key of the state object, the transcript an
array under `messages` — visible in the shown code, done by no adapter.

## Consequences

- `cases/typesafe/conversation_state.json` (the D6 wrapper) is
  withdrawn; its receipt stays under `receipts/2026-09-17-typesafe/` as
  the record of what was measured then.
- `docs/mapping-rules.md` MAP-14 §2 typesafe row and `spec/types.md`
  §DataPart prose updated.
- Ports: the typesafe dialect's state builder shrinks to D1+D2; four
  chat dialects gain the `data` case (D3). No new type, no new field.
